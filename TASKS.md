## Known limitations carried forward
- Catalogue: all 47 products are demo data (fictional "(Demo)" brands, illustrative prices, drawn demo pictures, demo stock); Fevicol products use the real brand name with placeholder prices. Real products, photos, prices, MRPs, GST/HSN codes, stock and specifications must be entered before going live
- Notifications: WhatsApp and SMS run on the mock providers (recorded, nothing sent) until real accounts are connected; WhatsApp messages started by the shop must use templates approved in WhatsApp Manager with the same variables in the same order as the shop's words; the bell refreshes every minute (no live push); messages go out within one cron interval in `cron` mode (immediately in `inline` mode); the "running late" check runs from `run_jobs`; a customer's own words in Hindi/Hinglish exist only where an administrator wrote them (built-in words are English)
- Smart cart / recommendations: "frequently bought together" needs real orders (empty on a new shop); alternatives are only suggested within a kind the compatibility engine recognises; budget mode can only plan jobs the Quantity AI / project calculators know, and drops whole lines rather than reducing quantities; bundle prices follow the live catalogue (a kit with an out-of-stock item shows it and can't be added until fixed)
- Compatibility: only the 13 rule pairs and the shop's links decide; other kinds of product get "not enough information" (add a rule in `catalog/compatibility/rules.py` or a shop link); facts must be in the listing (specifications such as Chuck Size, Sizes, Diameter, Material, Current Rating, Thread; sizes in variant names); nominal pipe sizes are compared as written ("1/2 inch"), not converted from mm; the engine's reasons are English in all three languages; replacements are searched among up to 500 published products per check
- Quantity AI: rules of thumb for a shopping list (labelled), not engineering; 8 calculators; pack sizes must be written in the variant name, options or size specs ("4 L", "Pack of 100", "Box (21.5 sq ft)"), otherwise one pack is suggested and flagged; a material is matched only when a product name/tags/category/variants contain all its search words, so new product kinds may need search words in `projects/templates.py`; the optional AI helper (~8 s on CPU with qwen2.5:3b) can still pick the wrong calculator for odd wording (the page says the details were read by AI); pack combinations are searched exhaustively up to 4 sizes and 20,000 combinations, single sizes beyond that
- Project builder: quantities are rules of thumb for a shopping list (labelled estimates), not an engineering calculation; 9 job types (gardening and "other" have no guided plan); a material is only matched when the catalogue has a product whose words all match its search words, so new product names may need search words in `projects/templates.py`; pack sizes are read from names/options/specs ("4 L", "Pack of 100") and default to one piece when absent (flagged "check the pack size")
- Voice: needs a browser with speech recognition (Chrome, Edge, Safari; not Firefox) unless server recognition is switched on (VPS); Chrome's recognition uses Google's speech service (the page says so); reading Hindi aloud needs a Hindi voice on the device (many Windows desktops have none: the answer is then shown only); romanised Hindi number words cover the common ones, not every spelling; "yes" adds only the lines shown in the current proposal; a signed-out shopper confirming several items gets the first added after sign-in and must say the others again
- Loyalty credits pay goods only (not the delivery fee); cashback uses the best single rule; credited cashback and expiry run from `run_jobs` (cron), so they appear within one cron interval of the moment they are due
- A return restores credits per unit without the cumulative rounding refunds use; any paise difference is capped by what was used and never exceeds it
- Photo search: off by default and needs a VPS-class machine for CLIP (~2 GB RAM, ~1.7 GB model) or Ollama (several GB); the item list is generic hardware plus the shop's subcategories, so an unusual item gets the closest kind or "not sure"; ~1.5 s per photo on a laptop CPU with ViT-L/14; HEIC photos must be converted (the page explains); the CLIP status shows "starting up" for 20–60 s after a server start
- Semantic search: the synonym/Hinglish tables are hand-written for hardware words (new product kinds may need entries in `semantic/expand.py`); the `hashing` default knows spelling, not meaning, so unseen descriptions rely on the tables unless the MiniLM model is installed; the model needs ~1 GB RAM and PyTorch (VPS, not shared hosting) and adds 10–20 s of warm-up at server start (keyword search meanwhile); the full rebuild from the dashboard runs inside the request (use the management command for a large catalogue with the model); with the model the main-set hit@1 is lower than tables-only (67% vs 74%) while hit@3 and unseen wording are better; benchmark labels fit the demo catalogue only
- AI assistant: understanding is rule-first with a small model (`qwen2.5:3b`) on top, so unusual phrasings can get a follow-up question or a broader search; answers on CPU take several seconds (first one loads the model); retrieval uses the configured search backend (hybrid since Phase 13); only English, Hindi and Hinglish; production runs in basic mode until an AI provider is chosen
- Riders are assigned by staff; there is no automatic assignment, no job offers to several riders, and a rider who does not react to a job is not timed out (staff reassign)
- After a failed delivery the rider is free at once; the store does not confirm that the goods came back before sending them out again or cancelling
- An order that was partly delivered (one shipment of several) can't be cancelled; the remaining shipment is sent out again, or handled by staff outside the system
- The rider's position is stored only as the latest point and at each step; there is no live map tracking for the customer
- Earnings are a simple base + per-km figure recorded per job and shown per rider in the dashboard; there are no payouts, incentives or settlement reports
- A rider carrying cash can take further jobs; there is no limit on cash in hand
- Changing `SECRET_KEY` invalidates delivery codes of deliveries that are out at that moment (customers get a new code from the order page)
- Proof photos are on the hosting disk under `PRIVATE_MEDIA_ROOT`; they are not cleaned up automatically and need to be part of the backups
- Delivery estimates use straight-line distance × a road factor unless OSRM is enabled; traffic, weather and one-way streets are not modelled. PIN-only addresses are estimated from the PIN's centre (or the zone radius when the PIN has no known centre)
- Rider wait is a simple queue model (riders on shift × turnaround time); riders' live positions and routes are not used for the ETA. In-house riders are a number on the store ("Own riders"), not tracked individually
- One delivery fee is charged per order, also when it ships from several stores (the primary shipment's zone rule)
- A split order is planned greedily (store covering most lines first), which is not always the mathematically best split; a line is never divided between stores, so 5 units with 3 + 3 in two stores can't be ordered together
- The plan reads stock before the reservation locks it. On PostgreSQL/MySQL two simultaneous orders for the last units at one store can make the second fail with `insufficient_stock` even if another store could have served it; the customer retries and gets the other store. (SQLite serialises transactions, so tests can't show this)
- Customers choose no delivery slot; standard delivery gets the next window. Estimates are not recalculated after the order is confirmed (delays are not pushed to the customer until Phase 10/20)
- Stores whose own riders have no accounts move orders through the delivery statuses by hand; those deliveries have no delivery code, photo or cash record
- Delivery zones, PIN codes and store delivery settings are managed in the dashboard (Phase 11); polygons are still entered as JSON in Django admin (no map editor)
- Public OpenStreetMap services (tiles, Nominatim, OSRM demo) have usage limits and no SLA (FREE_TOOLS.md)
- Offers have no "buy X get Y"/bundle or cashback types (cashback: Phase 17), and only one coupon per order
- Product listing prices stay the catalogue price; the offer discount appears in the cart (the badge says so), not as a reduced list price
- Razorpay is implemented but inactive until the owner adds keys and registers the webhook (DEPLOYMENT.md). Only one gateway at a time; switching providers leaves older attempts with their original provider
- Refund speed is Razorpay's `normal`; instant refunds, partial captures, EMI/offers configuration and payment links aren't used. Automatic refunds of *duplicate* payments refund the second payment in full
- Cron is needed in production for refund polling, reconciliation and expiry (inline mode covers refund submission only)
- Returns: no pickup scheduling (the delivery partner flow is Phase 10), no photo upload with the request, no exchanges or replacements, and no per-product return window (one global `RETURN_WINDOW_DAYS`). Staff handle returns in the dashboard (Phase 11), which asks for a reason when rejecting
- COD refunds are paid back by staff and recorded with a reference; there is no cash-drawer reconciliation or delivery-partner cash handover yet (Phase 10)
- Concurrency is proven with real threads on SQLite (serialised writes). PostgreSQL/MySQL rely on the same `select_for_update` locks but the suite has not yet run against those servers (Phase 26)
- Unpaid online orders keep their stock reserved for up to `PAYMENT_EXPIRY_MINUTES` (+ the cron interval) before expiry releases it
- Cart "save for later" uses the wishlist (per product, not per variant)
- Plain keyword search (the fallback, and `CATALOG_SEARCH_BACKEND=apps.catalog.search.KeywordSearchBackend`) is still substring based ("tap" also matches "tape"); the hybrid default filters those accidents
- Specification filters need consistent spec names/values in the admin; free-text variant attributes are not filterable (structured options are, since Phase 15/16)
- Pages set title, description, canonical URL and JSON-LD client-side (no server-side rendering); search engines that don't run JavaScript see only the sitemap URLs
- Recently viewed is kept per browser (not per account); search words become filters only for option/spec/category values that exist exactly in the catalogue
- Fast-delivery flags on listings are based on the best store for the PIN's centre (cached 60 s), like `/delivery/check/`; the exact time for an address is calculated in the cart and at checkout
- Delivery partners are verified by administrators in the dashboard (Delivery → Delivery partners); giving a person the delivery-partner role (Customers) creates the rider record, which needs a phone number on the account. Vehicle details are entered by an administrator there or in Django admin
- Email verification is not implemented yet (`email_verified` is reset on email change)
- A local dev server stopped with `Stop-Process -Force` makes Git Bash report exit 127 (the venv `python.exe` launcher loses its child); stop it with Ctrl+C in normal use
